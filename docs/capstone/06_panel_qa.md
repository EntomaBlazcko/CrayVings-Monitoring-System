# Deliverable 6 — Likely Panel Questions (honest answers)

Every answer was checked against live catalog output, `server.cjs` code, or both on
2026-10-18. **ASSUMPTION** marks anything not provable from those sources (policy
blocks reading `.env`).

---

### Q1. Your `sms_logs.recipient_phone` has no foreign key — is that an oversight?

No — a foreign key requires a **full** unique index or PK on the referenced column.
The only unique index on `authorized_recipients.phone_number` is partial
(`idx_recipients_phone_active`, `WHERE archived_at IS NULL`), which PostgreSQL refuses
as an FK target, and history must survive the recipient-purge DELETE endpoint anyway.
Instead, BEFORE INSERT trigger `trg_sms_logs_recipient` raises
`ERRCODE = 'foreign_key_violation'` when the phone matches no recipient. Honest limit:
the check is **insert-time only** — a later purge does not scrub rows that were valid
when sent (a feature for audit, not a bug).

### Q2. Why do log tables store `user_name` / `acknowledged_by` as text when `user_id` exists?

Because audit must outlive identity: `activity_logs.user_id` and
`user_deletion_requests.user_id` are `ON DELETE SET NULL` (verified FK definitions;
2 980 activity rows already have `NULL` user_id), and usernames are reusable once
archived (partial unique `WHERE status <> 'archived'`). The text snapshot answers
"*who*" forever; the FK is a live convenience link. Both together = 3NF with a
documented, single-purpose redundancy.

### Q3. Isn't `devices.last_seen` a 3NF violation?

It is a **derived cache**: the last ingest timestamp, overwritten on every POST
/sensor. Storing it costs one redundant write to avoid a `MAX(timestamp)` scan over
`sensors` on every dashboard/health request (and `sensors` purges at 30 days, so the
question could not even be answered from history later). Listed in the defense sentence
in `04_normalization.md` as one of three justified caches.

### Q4. Why is `last_alerts` keyed by (device_id, sensor_key) instead of a surrogate?

Because its semantics are *current state per board per parameter* — that pair **is**
the natural key, there is exactly one row per pair (upsert, not append), and nothing
but the pair determines the rest (status, value, timestamp). A surrogate would just
hide the same uniqueness behind an index.

### Q5. Why is there no `tanks` table? Is `tank_name` on `devices` a 3NF violation?

Not a violation: `tank_name` depends directly on the device's PK, and the business rule
is 1:1 (BR1) — a tank has no independent attributes, relationships, or lifetime outside
its board. A separate table would add a join with zero redundancy removed. If a tank
ever hosts multiple boards or gains its own history, we would split it then — that is a
stated evolution point, not current normal form.

### Q6. Why `CHECK (id = 1)` on `sensor_settings` instead of a key/value table or env vars?

Thresholds must be editable by admins at runtime, audited (`system_logs` old/new
values), and read on every alert evaluation. One row with typed columns gives that
without joins; the singleton CHECK stops a second row from ever making the app's
"read the settings" query ambiguous. Key/value storage would re-introduce type strings
and parsing; env vars would lose runtime editing and audit.

### Q7. Why isn't `owner` a value in `users.role`?

`role` is a CHECK domain of exactly `'admin'`/`'user'`. The owner is **derived per
request**: `isOwnerUser()` (server.cjs:755–770) compares username/email against
configured `ADMIN_USERNAME`/`ADMIN_EMAIL` and returns an `owner: true` flag. So
ownership can be transferred by configuration with no data migration, the owner row has
no special DB privileges to leak, and protection checks (cannot archive the owner,
server.cjs:3510) all funnel through one function.

### Q8. Why are username/email only *partially* unique?

Archived accounts must keep their audit history **and** the login name must become
re-usable: `CREATE UNIQUE INDEX ... WHERE status <> 'archived'`. Real proof in the data:
rows 131 and 132 both have username `User` — both archived, no violation. A full unique
index would have made re-registering a placeholder name impossible.

### Q9. A sensor fails mid-report — what lands in the database? Does ammonia = 0 fire an alarm?

`NULL`, never `0`: the wire sentinels (temperature `-1`/`0`, level `-1`, ammonia `-1`)
are converted at ingest, migration 022 removed every fake-`0` default, and each CHECKs
explicitly allows `NULL` first (`... IS NULL OR (value BETWEEN ...)`). UI renders `--`.
**Honest quirk:** the scheduled alert sweep evaluates via `Number(null) = 0`
(server.cjs:1829), so a *missing* ammonia reading with `ammonia_min > 0` currently
evaluates as 0 ppm → critical **"Low"**. Direction is fail-safe (loud on missing data,
never silently green) — documented as an assumption/known quirk, not changed in this
phase. Current `ammonia_min = 0.25` (set 2026-10-18 via the Settings page).

### Q10. `bcrypt` is in `package.json` — so passwords are bcrypt, right?

No. Nothing imports bcrypt (or `jsonwebtoken`/`pino` — present but unused). Passwords
use `crypto.pbkdf2Sync(password, salt, iterations, keylen, digest)` with a per-hash salt
and the iteration count embedded in the stored string (`hashPassword`/`verifyPassword`,
server.cjs:264–281); `needsRehash()` upgrades old hashes transparently. Sessions are
separate: `HttpOnly` cookie + SHA-256-hashed token in `users.token`.

### Q11. Why is `device_secret` stored plainly instead of hashed?

It must be reproduced exactly: the ESP32 sends it as a Bearer credential that is
compared in constant time, and the rotation response returns the new secret to the
admin so it can be placed on the board (server.cjs:2879 — hashing would make both
impossible). Risk is mitigated by constant-time
comparison, rotation with grace window (`device_secret_prev` + expiry pair CHECK), and
DB access control — noted honestly as a hardening candidate, not a hidden flaw.

### Q12. You claim "history", yet sensors are purged after 30 days?

Retention windows (code defaults, env-overridable, `0` disables): sensor readings 30 d,
`system_logs` 30 d, `sms_logs` 30 d, `activity_logs` 90 d. **ASSUMPTION:** actual
`.env` values are not read by policy. What is *never* purged: `devices`, `users`,
`last_alerts`, `sensor_settings`, archive-workflow (legacy "deletion") rows, `schema_migrations`. So
"all-time" means registry + current state + audit/ledger; raw readings are a rolling
window — a stated storage trade-off, and reports/graphs operate on the retained window.

### Q13. Why don't `sensors` / `last_alerts` use `ON DELETE CASCADE` like the override tables?

Deliberate asymmetry: readings and alert state must never silently disappear with their
board — FKs are `NO ACTION`, so deleting a device that still has readings/alerts is
refused until handled explicitly. Convenience children (overrides, calibration, workflow
history) cascade; audit children (`activity_logs`, `system_logs`,
`user_deletion_requests`) `SET NULL` to preserve history; high-value state refuses.

### Q14. Why do `system_logs.old_value` / `new_value` hold text snapshots instead of referencing rows?

They are `varchar(50)` snapshots of heterogeneous settings (a temperature, a phone
flag, a string) at the moment of change — the point is what the value *was*, which a
live FK cannot give after the row changes or is purged. This is the same snapshot
principle as Q2, applied to values instead of identities.

### Q15. OTPs are salted-hashed but session tokens are only SHA-256 — why the difference?

Entropy: an OTP is short and guessable (attempts capped by `max_attempts = 5`), so a
per-row salt defeats precomputation; a session token is a high-entropy random value
(`crypto`-generated), where salting adds nothing an attacker can precompute. Both are
never stored raw; the OTP additionally carries expiry, attempt counters, and `used_at`.

## If pushed beyond these answers

Admit the three documented soft spots without flinching (they are in the docs on
purpose): the `Number(null) = 0` alert quirk (Q9), recipients archived with
`is_active` still `true` (send filter requires both flags — `01_data_dictionary.md`
§13), and unused `schema_migrations.checksum` (deferred item D9). Deferred hardening
list also carries F1 soft-ref `*_by_id`, E3 retention review, D8 redundant
`sensors.device_id` index.

Table sensors {
  id int [pk, increment]
  device_id varchar(50) [not null]
  // No DEFAULT since migration 022 (defect D1, fixed): a failed sensor is NULL,
  // which the CHECKs below accept — the old vestigial DEFAULT 0 was rejected by
  // chk_sensors_temperature_valid, so it could never legally fire anyway.
  temperature decimal(5,2)
  water_level decimal(5,2)
  // precision is (5,2), not (5,3) - verified against the live database
  ammonia decimal(5,2)
  // Raw HC-SR04 distance (migration 018). NULL = not reported by the firmware
  // or a failed sensor. A lossy percentage alone cannot be recalibrated later.
  water_distance_cm decimal(6,2)
  timestamp timestamptz [default: `now()`]

  // Range checks (migration 009). Each allows NULL - a NULL reading means the
  // sensor failed, which is recorded rather than rejected.
  //   chk_sensors_temperature_valid: 0 < temperature <= 100
  //   chk_sensors_water_level_valid:  0 <= water_level <= 200
  //   chk_sensors_ammonia_valid:      0 <= ammonia <= 1000
  //   chk_sensors_water_distance_valid (migration 018): NULL or 0 < water_distance_cm <= 400

  Indexes {
    (timestamp) [name: 'idx_sensors_timestamp']
    (device_id) [name: 'idx_sensors_device_id']

// index. Migration 019 links activity_logs.user_id -> users.id instead (drawn
// above), leaving user_name as the display string. The name column stays
// unenforced on purpose, not by accident.

// (2) sms_logs.recipient_phone > authorized_recipients.phone_number
//     -- STRUCTURALLY IMPOSSIBLE, not a gap.
// phone_number is unique only via the PARTIAL index idx_recipients_phone_active,
// and PostgreSQL requires a foreign key to reference a UNIQUE constraint or a
// NON-PARTIAL unique index. Integrity is enforced instead by trigger
// trg_sms_logs_recipient (function check_sms_logs_recipient, migration 016),
// which rejects INSERT and UPDATE OF recipient_phone when no matching recipient
// exists. ERD tools do not draw triggers.

// (3) Soft references by username: activity_logs.user_name,
// system_logs.acknowledged_by, devices.archived_by,
// users.pending_deletion_requested_by, and requester_username / approver /
// executed_by / otp_verified_by on user_deletion_requests, plus recorded_by on
// user_deletion_request_status_history. Because usernames can be reused after
// archiving, an old audit row may point at a different person.
// (activity_logs.user_id and user_deletion_requests.user_id ARE drawn above,
// because those are real foreign keys - just not on the name column.)
