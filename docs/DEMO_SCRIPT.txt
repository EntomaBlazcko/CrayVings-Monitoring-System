 CRAyViNGs MONITORING - FAILURE-HANDLING DEMO SCRIPT

-------------------------------------------------------------------------------
 DEMO 1 - FIRMWARE WATCHDOG + SAFE MODE   (~90s total)
-------------------------------------------------------------------------------
 GOAL: show a hung firmware loop does not brick the device.

 SETUP (do this in the Arduino IDE BEFORE the demo, and revert before
        uploading the demo firmware):
     1. Open water_monitoring_system.ino
     2. In loop(), temporarily add:   while (1) { yield(); }
     3. Upload to the ESP32.
     4. AFTER the demo, remove the while(1) and upload the normal firmware.

 SCRIPT (paste the narration, keep it natural):
   "This is our ESP32 at the tank. Watch what happens when the firmware hangs.
    We've injected an infinite loop into the main loop - exactly the kind of
    bug that normally bricks a bare microcontroller."

   Step 1  - Power on / reset the device. loop() is now instantly stuck.
   Step 2  - Wait ~30 seconds. The chip resets itself.
             POINT at the serial monitor:
               [WDT] Task watchdog armed (30s timeout)
               [WDT] Boot after watchdog reset (reason=...) -> Safe Mode
   Step 3  - The display shows:  SAFE MODE  with the last known-good
             temperature / water level / NH3 values, and the onboard LED
             blinks.
             "The watchdog detected the hang, rebooted the chip, and the
              device came back in Safe Mode showing its last real readings -
              not a black screen."
   Step 4  - Because sensor POSTs resume on the background task, the first
             successful send flips it back to normal operation automatically.
             Serial: "[SAFE MODE] Sensor POST OK - recovery complete".
   Step 5  - "No reset button, no flashing tool - it recovered by itself.
              That's the difference between a sensor and an emergency."

 NOTES
   - The blink is driven by millis(), so Safe Mode itself can never starve the
     watchdog (no infinite reboot loop).
   - If the board has no LED on GPIO2, the SAFE MODE screen alone still proves
     the recovery.

 DEMO 2 - WIFI OUTAGE + EXPONENTIAL BACKOFF   (~60s total)
-------------------------------------------------------------------------------
 GOAL: show graded retry behavior on network loss (real, no code change).

   Step 1  - Triple-tap top-left to open the WiFi config portal, or just turn
             off the router / create a hotspot the device can't reach.
   Step 2  - Watch the serial monitor:
               [WIFI] Reconnect attempt 1 (next backoff 1s)
               [WIFI] Reconnect attempt 2 (next backoff 2s)
               [WIFI] Reconnect attempt 4 (next backoff 4s)
             "Notice the retries space out geometrically - 1, 2, 4, 8 seconds.
              We're not hammering the router when there's nothing to reach."
   Step 3  - Switch the router back on.
             Serial: "[WIFI] Reconnected - fail streak 0 cleared, backoff reset"
   Step 4  - "When connectivity returns, the streak clears and normal sending
              resumes at the regular interval. No reboot needed."

-------------------------------------------------------------------------------
 DEMO 3 - SMS CIRCUIT BREAKER   (~90s total)
-------------------------------------------------------------------------------
 GOAL: show the backend stops hammering a dead SMS gateway and recovers.

 SETUP (do BEFORE the demo, on the PC running the backend):
     1. Open C:\Windows\System32\drivers\etc\hosts (as Administrator) and add:
          127.0.0.1 api.httpsms.com
     2. Save. (This points the HTTPSMS API at nothing, so sends fail fast.)
     3. Have the dashboard open on the Settings > SMS panel.

 SCRIPT:
   Step 1  - Trigger a few SMS alerts (e.g. temporarily set the temperature
             threshold below the current reading and save, then touch the
             tank temp sensor). Each alert alerts 2+ recipients = 2 attempts.
   Step 2  - After 5 consecutive failures the server logs:
               SMS circuit breaker OPEN after 5 consecutive failures
             and every subsequent alert fails fast:
               SMS circuit breaker OPEN - HTTPSMS send skipped (...)
             The Settings SMS panel shows a red banner: "SMS circuit breaker
             OPEN". Show GET /alert/sms-health in a browser:
               "circuitBreaker":{"state":"OPEN","consecutiveFailures":5,...}
             "Once a gateway is clearly down, further attempts are a waste -
              they'd hammer a dead API, risk a ban, and burn our daily cap.
              So the breaker trips OPEN and we stop trying for 60 seconds."
   Step 3  - Remove the hosts line and save (restores the real gateway).
             Narrate: "After the cooldown, the breaker goes HALF_OPEN and
              allows exactly one probe..."
             On the next alert the probe succeeds:
               "SMS circuit breaker HALF_OPEN -> CLOSED after successful send"
             Panel returns to normal.
   Step 4  - "Automatic recovery - and we never lost the ability to watch the
              tank. The circuit protects the provider link; the alerts remain
              queued and re-deliver once the link is healthy."

 CLEANUP
   - Remove the 127.0.0.1 hosts line if demo 3 was the last one.
   - Restore settings thresholds to real values.
   - The failed sms_logs rows stay visible in the Settings SMS history (useful
      to show "failed" status reconciliation during Q&A).

===============================================================================
 Q&A AMMUNITION - WHY THESE MECHANISMS
===============================================================================
   - Watchdog  -> firmware hang is the #1 way a deployed ESP32 'goes dark';
                  auto-reset + last-known-values keeps data continuity.
   - Backoff   -> bounds load on a dead AP and makes recovery deterministic.
   - Breaker   -> provider outages are inevitable; the breaker caps failure
                  cost (SMS caps, API bans) and recovers without an admin.
   - Together  -> three different failure domains (hardware, network, cloud)
                  demonstrated in one system - the point of "production-grade".
