================================================================================
1. OVERVIEW
================================================================================

A web flasher allows end-users to flash/update ESP32 firmware directly from
the browser using the Web Serial API. No Arduino IDE, no Python, no CLI tools
required. The user simply connects the ESP32 via USB, selects firmware, and
clicks "Flash."

This is designed for end-user convenience - aquaculture operators who may not
be technical can update their ESP32 devices from the dashboard.

5. ESP32 FLASH MEMORY LAYOUT
================================================================================

The ESP32 uses a partitioned flash memory. The web flasher must write each
binary to the correct memory offset:

  Offset      Size       File                          Description
  ----------  ---------  ----------------------------  -------------------
  0x1000      ~28 KB     water_monitoring_system.ino.bootloader.bin  Bootloader
  0x8000      ~4 KB      water_monitoring_system.ino.partitions.bin  Partition table
  0x10000     ~1.3 MB    water_monitoring_system.ino.bin             Application firmware

  TOTAL: ~1.4 MB per flash

  NOTE: These offsets are for standard ESP32 (not ESP32-S2/S3/C3).
        The ESP32 DevKit V1 uses the standard ESP32 chip.

 9. useEspFlasher HOOK API
================================================================================

The custom hook will expose:

  NOTE: esptool-js is callback-driven (ESPLoader writeFlash, Transport). The
        hook wraps these in Promise-based helpers and forwards onProgress /
        onConsole callbacks into the React state above.

  States:
    - status: "idle" | "connecting" | "connected" | "flashing" | "done" | "error"
    - progress: number (0-100)
    - logMessages: string[] (terminal output lines)
    - error: string | null
    - isSupported: boolean (WebSerial available)
    - chipInfo: { name: string, flashSize: string } | null

  Functions:
    - checkBrowserSupport(): boolean
        Returns true if Web Serial API is available

    - connect(): Promise<void>
        Opens the browser's serial port picker
        Connects to ESP32 ROM bootloader
        Reads chip info

    - flash(manifest): Promise<void>
        Erases flash (if selected)
        Writes bootloader to 0x1000
        Writes partitions to 0x8000
        Writes application to 0x10000
        Resets device

    - disconnect(): void
        Closes serial port cleanly

    - abort(): void
        Cancels ongoing flash operation (AbortController)

  Import:
    import { ESPLoader, Transport } from "esptool-js";

10. USER FLOW
================================================================================

  1. User logs into CRAYvings dashboard
  2. User (admin or owner) opens Settings > Firmware Flasher
  3. Page loads and checks browser compatibility
     - If unsupported: show error + link to Chrome/Edge
     - If supported: show green checkmark
  4. User connects ESP32 via USB cable
  5. User clicks "Connect Device"
     - Browser shows serial port picker popup
     - User selects the ESP32 port (e.g., "USB-SERIAL CH340")
     - ESP32 connects and chip info is displayed
  6. User selects firmware (pre-built CRAYvings v1.0)
  7. User clicks "Flash Firmware"
     - Progress bar appears
     - Terminal output shows real-time progress
  8. If connection fails immediately:
     - UI shows instructions to enter download mode:
       "Hold the BOOT button on your ESP32, press and release
        the RST button, then release BOOT."
  9. Flash completes
     - Status: "Flash complete! Device is restarting."
     - Device automatically resets and starts running new firmware

12. CONSTRAINTS
================================================================================

  - USB cable required (not wireless/OTA)

  - Arduino IDE is needed for initial compilation (not for end users)

13. ALTERNATIVE APPROACHES CONSIDERED
================================================================================

  Option A: ESP Web Tools (esphome.github.io/esp-web-tools/)
    - Pros: Simplest to implement, uses <esp-web-install-button> web component
    - Pros: Automatic chip detection, manifest-based firmware selection
    - Cons: Limited UI customization, designed for ESPHome-style installs
    - Verdict: Too opinionated for custom firmware

  Option B: espcdcflash (USB CDC only)
    - Pros: Focused, clean API
    - Cons: ESP32-S3 only, does not support standard ESP32
    - Verdict: Wrong chip family for this project

  Option C: esptool-js (SELECTED)
    - Pros: Official Espressif library, full ESP32 support
    - Pros: Full control over UI and flashing behavior
    - Pros: Active maintenance, large community
    - Cons: More code to write for UI
    - Verdict: Best fit for custom React integration

  Option D: Standalone ESP-32-WebFlasher
    - Pros: Pre-built, works out of the box
    - Cons: Separate app, not integrated into dashboard
    - Cons: Hardcoded firmware list
    - Verdict: Not integrated enough for end-user experience

18. KNOWN ISSUE - "The port is already open" (UNRESOLVED as of 2026-09-16)
================================================================================

SYMPTOM:
  Settings > Firmware Flasher > Connect Device fails with:
    "Failed to execute 'open' on 'SerialPort': The port is already open."
  The formal error card shows:
    Title: "Serial port unavailable" / "Serial port still open"
    Message: "The computer could not open the selected serial port..." or
             "The selected port is still open from an earlier connection..."

ENVIRONMENT:
  - OS: Windows 10/11 (win32)
  - Browser: Brave (Chromium-based) - only ONE tab open, no other tabs/programs
    use the serial port.
  - Boards: DOIT ESP32 DEVKIT V1 (production) + spare NodeMCU-32S (ESP32).
  - Backend (server.cjs) does NOT open any serial port - confirmed by grep for
    serialport/COM in server.cjs. This is purely a browser-level conflict.

OBSERVED SEQUENCE:
  1. First attempt: "Failed to open serial port" (OS refused) - user had other
     programs/tabs and/or old Brave session holding the port.
  2. After closing other tabs/programs: "The port is already open" - the port
     is still flagged open inside Brave's browser process (stale Web Serial
     state that survives tab reload; only survives a FULL browser restart).
  3. Test not yet repeated after a full Brave restart (2026-09-16).

WHAT WAS ALREADY TRIED / IMPLEMENTED (in useEspFlasher.ts + FirmwareFlasher.tsx):
  - Formal error cards via classifyFlashError() - maps raw Web Serial errors to
    friendly, actionable guidance (no port selected / port unavailable / port
    still open / no communication / unexpected).
  - Auto-recovery in connect():
      a) Closes any transport this page already holds before picking a device
         (a finished flash keeps the port open after hard_reset).
      b) If the picked port is already open (readable/writable != null), closes
         it first.
      c) Retries port.open() up to 5 times with a 200ms delay when "already
         open" is thrown (async stream release race).
  - closeTransport() now force-releases the underlying SerialPort (transport
    .disconnect() plus device.close()) so a stale connection can't block
    reconnects.
  - Known-error detail is also mirrored into the Terminal Output log.

REMAINING HYPOTHESES IF "ALREADY OPEN" PERSISTS AFTER A FULL BROWSER RESTART:
  1. Chromium serial-state bug - the port stays flagged open in the browser
     process even after page unload; only closing the whole browser clears it.
     TEST: Close Brave completely (Task Manager -> end all brave.exe), reopen,
           reconnect the board, retry.
  2. Wrong port picked - the user may be selecting the production unit's port
     (or the picker lists a port that is actually in use by something else).
     TEST: In Device Manager > Ports (COM & LPT), note which COM is the
           NodeMCU-32S (CH340/CP2102) and pick exactly that one.
  3. Driver issue - missing/incompatible CH340 or CP2102 driver still leaves
     the port ownerless/confused at OS level. TEST: reinstall driver, reboot.
  4. Multiple Origin entries - if the dashboard is served over http://localhost
     AND the LAN IP/HTTPS simultaneously, Brave tracks ports per-origin; a
     second origin connection would conflict. TEST: use only ONE URL.
  5. port.close() not fully awaited - if retries (5x) still race, increase the
     retry delay to 500ms or call esptool-js Transport.waitForUnlock() after
     close.

NEXT TIME YOU TACKLE THIS:
  1. First reproduce after a FULL Brave restart (see hypothesis 1).
  2. Check navigator.serial.getPorts() from the browser console - it lists all
     ports Brave still considers "already connected" for this origin.
  3. If getPorts() shows the port open with no tab using it, it is the browser
     bug in hypothesis 1 - document and add a "restart your browser" hint to the
     error tip.
  4. If it only happens on one specific COM port, chase hypothesis 2/3.
  5. Consider pre-routing: call navigator.serial.getPorts() before requestPort()
     and close any held ports before opening.
